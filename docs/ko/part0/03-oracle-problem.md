# 3. 오라클 문제 — 무엇을 버그라 부를 것인가

**Part 0 · 퍼징의 뼈대**

2장의 퍼저는 오라클이 한 줄이었습니다. `if crashed`. 예외가 나면 버그.
간단하고, 그래서 위험합니다. **크래시하지 않는 버그는 전부 못 봅니다.**

오라클은 퍼징에서 가장 어려운 부품입니다. 생성기는 대충 만들어도 언젠가
정답 입력을 던집니다. 하지만 정답이 눈앞에 와도 오라클이 "이건 버그야"라고
말하지 못하면, 그냥 지나갑니다. 이 장은 그 문제를 정면으로 봅니다.

## 이 장에서 답할 질문

- 왜 "크래시 = 버그"는 대부분의 버그를 놓치는가
- 오라클에는 어떤 종류가 있는가
- 세 도메인(web2·API·web3)의 오라클은 이 분류의 어디에 놓이는가

## 5요소 위치

이 장이 다루는 요소: **오라클**

## 1. 크래시 오라클의 맹점

크래시하지 않지만 틀린 함수를 봅시다 (`labs/part0/oracle_demo.py`).
절댓값 함수인데, `x = -7` 에서만 조용히 틀립니다.

```python
def my_abs(x: int) -> int:
    if x == -7:
        return -7          # 버그: 음수를 그대로 반환. 예외는 안 난다.
    return x if x >= 0 else -x
```

이 버그를 두 오라클로 찾아봅니다.

```bash
cd labs/part0
python3 oracle_demo.py
```

```text
크래시 오라클: 0건 발견
차분 오라클:   1건 발견 → x=[-7]
```

크래시 오라클은 -100부터 100까지 전부 던져도 **0건**입니다.
`my_abs` 가 예외를 안 내니까요. 2장의 퍼저를 이 함수에 붙이면
영원히 "버그 없음"이라 보고합니다. 하지만 버그는 거기 있습니다.

## 2. 오라클의 종류

"무엇을 버그라 부를 것인가"에는 여러 답이 있고, 각각이 다른 종류의 버그를 잡습니다.

### 크래시 오라클

예외·세그폴트·패닉. 가장 싸고(공짜) 가장 명확합니다.
메모리 안전성 버그(C/C++의 버퍼 오버플로)를 잡는 데 강력합니다.
단점: 조용한 논리 오류를 전부 놓칩니다.

### 차분 오라클 (differential)

**두 구현의 답을 비교합니다.** 위 데모가 이겁니다 — `my_abs` 와
신뢰하는 `abs` 를 비교해 `x=-7` 을 잡았습니다.

```python
def differential_oracle(lo, hi):
    return [x for x in range(lo, hi) if my_abs(x) != ref_abs(x)]
```

레퍼런스 구현이 있을 때 강력합니다. 두 JSON 파서, 두 SSL 라이브러리,
최적화 켠 컴파일과 끈 컴파일 — 답이 갈리면 최소한 하나는 버그입니다.
Part 1 의 `/search` 응답 크기 비교(6장)도 실은 차분 오라클의 일종입니다 —
"미스 기준선과 다르면 히트".

### 속성/불변식 오라클 (property / invariant)

레퍼런스 없이, **항상 참이어야 하는 성질**을 검사합니다.
`abs(x) >= 0` 은 모든 `x` 에 참이어야 합니다. 이 성질을 오라클로 쓰면
레퍼런스 `abs` 없이도 `my_abs(-7) == -7 < 0` 에서 위반을 잡습니다.

```python
assert my_abs(x) >= 0          # 불변식: 절댓값은 음수가 아니다
```

이게 Part 2(Schemathesis 의 "응답은 스키마를 만족해야 한다")와
Part 3(스마트컨트랙트의 "총공급량은 보존되어야 한다") 전체의 원리입니다.
**불변식을 잘 쓰는 것이 API·web3 퍼징의 핵심 기술입니다.**

### 그 밖의 오라클

- **타임아웃**: 정상은 즉시 끝나야 하는데 안 끝난다 → 무한루프·ReDoS.
  Part 1 의 타이밍 오라클(6장)과 사촌입니다.
- **정화 오라클 (sanitizer)**: ASan·UBSan 처럼 런타임에 미정의 동작을
  감지하는 계측. C/C++ 퍼징의 표준 짝입니다.
- **메모리·리소스**: 누수, 과도한 할당.

## 3. 오라클은 "어느 축을 보느냐"의 사다리

Part 1 의 6장에서 오라클을 "누설 축의 사다리"라 불렀습니다 —
코드 → 크기 → 시간. 이 장의 분류는 그 사다리를 일반화한 것입니다.

| 오라클 | 무엇을 버그로 보나 | 이 교재에서 |
|--------|--------------------|-------------|
| 크래시 | 예외·패닉 | 2장 (장난감 퍼저) |
| 차분 | 두 구현의 답이 다름 | 6장 (응답 크기 차분) |
| 불변식 | 항상 참이어야 할 성질 위반 | 9·15장 (스키마·컨트랙트) |
| 타임아웃 | 안 끝남 | 6장 (타이밍) |

**오라클이 약하면 강한 생성기도 소용없습니다.** 감사에서 "퍼징 돌렸는데
아무것도 안 나왔다"의 절반은 생성기 문제가 아니라 오라클 문제입니다 —
크래시만 보고 있었던 겁니다.

## 4. 오라클의 대가: 거짓 양성

강한 오라클일수록 대가가 있습니다. **거짓 양성**입니다.
불변식을 너무 빡빡하게 잡으면, 버그가 아닌 정상 동작도 위반으로 신고합니다.
6장에서 타이밍 오라클이 지터에 무너져 거짓 양성을 쏟아낸 걸 봤습니다.

그래서 오라클 설계는 균형입니다.

- **너무 약하면** (크래시만): 진짜 버그를 놓친다 (거짓 음성)
- **너무 강하면** (빡빡한 불변식): 정상을 버그라 우긴다 (거짓 양성)

좋은 오라클은 "이게 정말 버그가 맞나?"를 사람이 최소한으로 판단하게 만듭니다.
불변식을 정확히 고르는 기술 — 이게 Part 3(15장)에서 가장 깊이 다루는 주제입니다.

## 정리

- "크래시 = 버그"는 가장 싸지만, 조용한 논리 버그를 전부 놓친다 (실측: 0건 vs 차분 1건).
- 오라클의 종류: 크래시 · 차분 · 불변식 · 타임아웃 · 정화.
- 세 도메인의 오라클은 이 분류 위에 놓인다 — 6장 크기차분, 9장 스키마, 15장 불변식.
- 오라클 설계는 거짓 음성(약함)과 거짓 양성(강함)의 균형이다.

이걸로 Part 0 이 끝납니다. 입력공간(1장), 다섯 요소(2장), 오라클(3장).
이제 이 뼈대를 실제 도메인에 붙입니다. Part 1 은 이미 봤습니다 —
web2 에서 생성은 워드리스트, 오라클은 응답 차분이었습니다.
Part 2 는 API 로 갑니다. 거기선 **스키마가 생성기이자 오라클**입니다.
