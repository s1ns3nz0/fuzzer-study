# 1. 입력공간과 탐색 — 퍼징이란 무엇인가

**Part 0 · 퍼징의 뼈대**

이 교재 전체가 이 한 장에 기댑니다. 여기서 퍼징을 하나의 정의로 못 박고,
나머지 15장은 그 정의가 web2·API·web3 에서 각각 어떻게 구현되는지를 따라갑니다.
도구는 3년 뒤에 바뀝니다. 이 장의 정의는 안 바뀝니다.

## 이 장에서 답할 질문

- 소프트웨어의 "입력공간"이란 무엇이고 왜 그렇게 큰가
- 다 시험해볼 수 없다면, 무엇을 대신 하는가
- 퍼징의 한 문장 정의는 무엇인가

## 1. 입력공간은 상상 이상으로 크다

함수 하나를 봅시다. 바이트 문자열을 받는 파서입니다.

```python
def process(data: bytes) -> str:
    ...
```

`data` 가 가질 수 있는 값은 몇 가지일까요? 길이 4바이트로만 한정해도
256⁴ = 약 43억 가지입니다. 길이 제한을 풀면 무한합니다.
이게 **입력공간**입니다 — 어떤 프로그램이 받을 수 있는 모든 입력의 집합.

실제 웹 애플리케이션의 입력공간은 이보다 훨씬 큽니다. 4장에서 보겠지만
경로 × 파라미터 × 헤더 × 메서드 × 세션 상태의 곱이니까요.
스마트컨트랙트라면 모든 함수 × 모든 인자 값 × 모든 호출 순서 × 모든 블록체인 상태입니다.

핵심은 하나입니다. **입력공간은 전부 시험해볼 수 없을 만큼 크다.**

## 2. 그래서 무작위? 아니, 편향된 탐색

전부 못 본다면 일부만 봐야 합니다. 가장 단순한 방법은 무작위입니다 —
아무 입력이나 마구 던지는 것. 이걸 **blind 퍼징**이라 부릅니다.
문제는, 흥미로운 버그일수록 무작위로는 도달할 수 없는 깊은 곳에 있다는 점입니다.

이 교재의 Part 0 랩에는 다음 버그가 있습니다 (`labs/part0/target.py`).
입력이 `FUZZ` 로 시작하고 다섯 번째 바이트가 `0x42` 일 때만 크래시합니다.

```python
if data[0:1] != b"F": return "reject: byte0"
if data[1:2] != b"U": return "reject: byte1"
if data[2:3] != b"Z": return "reject: byte2"
if data[3:4] != b"Z": return "reject: byte3"
if data[4] == 0x42: raise AssertionError("crash")   # ← 여기
```

무작위로 이 크래시에 닿으려면 앞 4바이트를 정확히 맞춰야 합니다.
확률은 1/256⁴ ≈ **43억분의 1**. 실제로 blind 퍼저를 300만 번 돌려도
못 찾습니다 (2장에서 실측합니다).

그래서 좋은 퍼징은 무작위가 아니라 **편향된** 탐색입니다.
"버그가 있을 법한 쪽으로" 탐색을 기울입니다. 무엇을 단서로 기울일까요?
바로 프로그램이 흘리는 신호입니다 — 응답 크기, 실행 시간, 밟은 코드 줄,
크래시. 이 신호로 다음 입력을 고르는 순간, 43억분의 1이 수천 분의 1이 됩니다.
2장에서 이걸 직접 만듭니다.

## 3. 퍼징의 정의

이제 한 문장으로 못 박습니다.

> **퍼징이란, 너무 커서 다 볼 수 없는 입력공간을, 유한한 시간 안에,
> 버그가 있을 법한 쪽으로 편향되게 탐색하는 일이다.**

이 문장을 분해하면 이 교재의 목차가 나옵니다.

| 정의의 조각 | 대응하는 요소 | 다루는 곳 |
|-------------|---------------|-----------|
| "입력공간" | 무엇을 향해 던지나 | 4·8·12장 |
| "탐색한다" = 입력을 만든다 | **생성·변이** | 5·9·13장 |
| "버그가 있을 법한" = 버그를 판정한다 | **오라클** | 3·6·11·15장 |
| "편향되게" = 신호로 다음을 고른다 | **피드백·커버리지** | 2·14장 |

세 도메인의 도구는 완전히 다릅니다. `ffuf`, `Schemathesis`, `Foundry`.
공동체도 어휘도 다릅니다. 하지만 셋 다 이 정의의 구현입니다.
그래서 하나를 이해하면 나머지가 빠릅니다.

## 4. 퍼징이 아닌 것

경계를 분명히 해둡니다.

- **정적 분석이 아니다.** 퍼징은 프로그램을 **실행**합니다. 코드를 읽어
  추론하는 게 아니라, 실제로 돌려서 무슨 일이 나는지 봅니다.
- **정형 검증이 아니다.** 퍼징은 "버그가 없음"을 증명하지 못합니다.
  버그를 **찾을** 뿐입니다. 못 찾았다고 없는 게 아닙니다.
- **완전하지 않다.** 유한한 시간에 유한한 입력만 봅니다. 커버리지가
  아무리 좋아도 입력공간의 극히 일부입니다.

이 한계 때문에 퍼징은 "얼마나 영리하게 편향시키느냐"의 게임이 됩니다.
그 편향의 엔진이 다음 장의 주제 — 5요소입니다.

## 정리

- 입력공간은 전부 시험할 수 없을 만큼 크다 (4바이트만 해도 43억 가지).
- 무작위(blind)로는 깊은 버그에 못 닿는다. 신호로 **편향된** 탐색을 한다.
- 퍼징 = 큰 입력공간을 유한 시간에 버그 쪽으로 편향 탐색하는 일.
- 이 정의의 조각들이 곧 5요소이고, 곧 이 교재의 목차다.

다음 장(2장)은 이 정의를 20여 줄의 Python 퍼저로 구현합니다.
그리고 위에서 말한 "43억분의 1이 수천 분의 1이 된다"를 직접 측정합니다.
