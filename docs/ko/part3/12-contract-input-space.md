# 12. 스마트컨트랙트 입력공간은 왜 다른가

**Part 3 · web3 감사**

Part 1 은 웹, Part 2 는 API 였습니다. 둘 다 "요청을 보내고 응답을 본다"는
익숙한 모델이었습니다. 스마트컨트랙트는 다릅니다. 여기서 퍼징의 5요소는
그대로지만, **입력공간의 모양과 오라클의 성격이 근본적으로 바뀝니다.**

이 장은 Part 3 의 지도입니다. 도구(Foundry)를 잡기 전에, 컨트랙트의
입력공간이 왜 다른지부터 이해합니다.

## 이 장에서 답할 질문

- 스마트컨트랙트의 입력공간은 무엇으로 이루어지는가
- 왜 "호출 순서"가 web2·API 보다 훨씬 중요한가
- web3 의 오라클은 왜 거의 전부 "불변식"인가

## 1. 컨트랙트의 입력공간

이 장의 랩 타겟은 작은 볼트입니다 (`labs/web3/src/Vault.sol`).
ETH 를 예치하면 1:1 로 지분(share)을 주고, 인출하면 돌려줍니다.

```solidity
contract Vault {
    mapping(address => uint256) public shares;
    uint256 public totalShares;

    function deposit() external payable { ... }
    function withdraw(uint256 amount) external { ... }
    function transfer(address to, uint256 amount) external { ... }
}
```

이 컨트랙트의 입력공간은 무엇일까요? web2 처럼 경로 × 파라미터가 아닙니다.

```
입력 = 함수 선택 × 인자 값 × 호출자(msg.sender) × 전송 ETH(msg.value)
       × 호출 순서 × 블록체인 상태(누적된 shares, 잔고, 블록 번호…)
```

세 함수뿐인데도 공간이 거대합니다. 그리고 web2·API 와 결정적으로 다른
축이 둘 있습니다.

## 2. 다른 점 1 — 상태는 영구히 누적된다

web2 요청은 대체로 독립적이었습니다. API 는 세션 상태가 있었지만
테스트 사이에 초기화할 수 있었습니다. 컨트랙트는 다릅니다.
**모든 트랜잭션이 영구 상태를 바꾸고, 그 상태 위에서 다음 트랜잭션이 돕니다.**

`deposit` 100 → `transfer` 30 → `withdraw` 50. 이 셋은 독립 사건이 아니라
같은 `shares` 매핑을 순차로 갈아엎습니다. 마지막 `withdraw` 가 뭘 하는지는
앞의 두 호출이 남긴 상태에 전적으로 달렸습니다.

## 3. 다른 점 2 — 호출 순서가 곧 버그의 원천

그래서 컨트랙트 퍼징에서 **호출 순서 자체가 일급 입력**입니다.
10장에서 API 시퀀스를 봤지만, 거기선 순서가 "인증을 얻는 절차"였습니다.
컨트랙트에서 순서는 그 자체가 취약점의 원천입니다.

- 재진입(reentrancy): 인출 도중 다시 인출을 호출하는 순서
- 프론트러닝: 남의 트랜잭션 앞에 끼어드는 순서
- 회계 오류: 특정 순서로만 드러나는 잔고 불일치

Part 3 랩의 버그도 순서에 숨어 있습니다. `deposit` 한 번으로는 안 보이고,
특정 `transfer` 호출이 뒤따라야만 드러납니다 (14장에서 잡습니다).

## 4. 그래서 오라클은 거의 전부 "불변식"

3장에서 오라클을 분류했습니다. 크래시, 차분, 불변식, 타임아웃.
web2 는 주로 크래시·차분(응답 크기)이었습니다. API 는 스키마 계약이었습니다.
**web3 는 거의 전부 불변식입니다.**

이유는 명확합니다. 컨트랙트에는 "정상 응답의 형태" 같은 게 없습니다.
대신 **항상 참이어야 할 회계적 성질**이 있습니다.

- 모든 사용자 지분의 합 = `totalShares`
- 컨트랙트가 보관한 ETH ≥ 갚아야 할 총액
- 총공급량은 mint/burn 외에는 불변
- 아무도 자기가 넣은 것보다 많이 빼갈 수 없다

이런 성질이 깨지면 그게 곧 취약점입니다. 그래서 web3 감사의 핵심 기술은
**"이 컨트랙트에서 항상 참이어야 할 것은 무엇인가"를 찾아내는 것** —
즉 좋은 불변식을 설계하는 것입니다. 도구(forge)는 불변식을 깨는 입력을
찾아주지만, **무엇이 불변식인지는 사람이 정해야 합니다.**

11장에서 "가장 가치 있는 버그는 사람이 불변식을 써야 하는 곳에 있다"고
했습니다. web3 는 그 원리가 지배하는 세계입니다.

## 정리

- 컨트랙트 입력공간 = 함수 × 인자 × 호출자 × ETH × **호출 순서 × 누적 상태**.
- 상태가 영구 누적되고, 호출 순서가 그 자체로 버그의 원천이다.
- 그래서 web3 오라클은 거의 전부 불변식이다 — 회계적 성질의 보존.
- 무엇이 불변식인지는 도구가 아니라 사람이 정한다. 그게 이 파트의 핵심 기술.
