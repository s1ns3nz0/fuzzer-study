# 4. 웹 입력공간 지도 — 경로·파라미터·헤더·상태

**Part 1 · web2 감사**

Part 0 에서 퍼징을 "너무 커서 다 볼 수 없는 입력공간을 편향되게 탐색하는 일"로
정의했습니다. 그 정의를 실제 대상에 적용하려면 먼저 답해야 할 질문이 있습니다.
**이 웹 애플리케이션의 입력공간은 정확히 무엇인가?**

이 장은 도구를 쓰지 않습니다. 퍼저를 돌리기 전에, 무엇을 향해 던질지를
그리는 장입니다. 지도 없이 던지는 퍼징은 워드리스트를 URL 경로에만 쏟아붓다
끝납니다 — 입력공간의 한 축만 훑는 셈입니다.

## 이 장에서 답할 질문

- 웹의 입력공간은 몇 개의 축으로 이루어지는가
- 크롤러가 보는 표면과 퍼저가 닿는 표면은 왜 다른가
- 경로 말고 어디에 입력이 숨는가 — 파라미터, 헤더, 메서드

## 5요소 위치

이 장이 다루는 요소: **입력공간 정의** (생성의 전제)

| 요소 | 이 장에서의 형태 |
|------|------------------|
| 생성 | 아직 안 함 — **무엇을 생성할지 그 대상(공간)을 먼저 정의** |
| 변이 | — |
| 오라클 | — |
| 피드백 | — |
| 커버리지 | — |

이 장은 5요소 중 어느 것도 실행하지 않습니다. 생성기가 입력을 만들려면
"어떤 공간에서" 만들지를 알아야 합니다. 그 공간을 그리는 게 이 장입니다.

## 준비

```bash
cd labs/web2
docker compose up --build -d
curl -s http://127.0.0.1:8080/    # 200 이면 준비 완료
```

!!! danger "실습 범위"
    대상은 본인의 `127.0.0.1:8080` 컨테이너뿐입니다. [범위와 안전](../scope-and-safety.md).

## 1. 크롤러가 보는 표면

가장 순진한 지도는 크롤링입니다. 시작 페이지에서 링크를 따라갑니다.
루트의 링크를 뽑아봅니다.

```bash
curl -s http://127.0.0.1:8080/ | grep -oE 'href="[^"]*"'
```

```text
href="/search?q=invoice"
href="/login"
```

크롤러가 이 앱에서 찾을 수 있는 건 두 개뿐입니다. `/search` 와 `/login`.
링크를 따라가는 방식은 **링크된 것만** 봅니다. 그리고 대부분의 흥미로운
표면은 링크되어 있지 않습니다 — 관리 페이지, 백업 파일, 디버그 엔드포인트,
옛 API. 아무도 홈페이지에서 `/admin-panel` 로 링크를 걸지 않습니다.

## 2. 크롤 표면과 퍼징 표면의 격차

크롤이 놓친 걸 퍼징이 잡습니다 (5장에서 쓴 명령을 미리 한 번 돌려봅니다).

```bash
ffuf -w wordlists/teaching.txt:FUZZ -u http://127.0.0.1:8080/FUZZ \
     -mc all -fc 404 -t 10
```

크롤과 비교하면:

| 방법 | 찾은 경로 |
|------|-----------|
| 크롤 | `/search`, `/login` (2개) |
| 퍼징 | 위 2개 **+** `/admin-panel`, `/backup.zip`, `/.env.bak`, `/user` |

퍼징이 크롤의 3배를 찾았습니다. 그리고 그 추가분이 감사에서 진짜 흥미로운
것들입니다 — 금지된 관리 패널(403), 백업 파일(40KB), 유출된 설정 파일.
**크롤은 개발자가 의도한 표면을 그리고, 퍼징은 개발자가 잊은 표면을 그립니다.**

이게 Part 1 전체의 동기입니다. 하지만 경로는 입력공간의 한 축일 뿐입니다.

## 3. 축 둘: 파라미터

같은 경로라도, 쿼리 파라미터의 **값**이 다르면 다른 입력입니다.
`/search` 는 경로 하나지만 `q` 값에 따라 응답이 완전히 달라집니다.

```bash
curl -s -o /dev/null -w '/search?q=invoice -> %{size_download}B\n' \
     "http://127.0.0.1:8080/search?q=invoice"
curl -s -o /dev/null -w '/search?q=zzz     -> %{size_download}B\n' \
     "http://127.0.0.1:8080/search?q=zzz"
```

```text
/search?q=invoice -> 137B
/search?q=zzz     -> 32B
```

경로는 동일한데 응답이 137B 대 32B. **파라미터 값이 곧 입력공간의 축**입니다.
경로만 퍼징하는 사람은 `/search` 를 "찾았다"고 체크하고 넘어가지만,
진짜 표면은 `q` 파라미터 안에 있습니다 (6장에서 여기를 퍼징합니다).

파라미터에는 이름 축도 있습니다. `q` 말고 `debug`, `admin`, `page` 같은
숨은 파라미터가 있을 수 있고, 그것도 워드리스트로 퍼징합니다.
**경로를 퍼징하듯 파라미터 이름도 퍼징합니다.**

## 4. 축 셋: 헤더

입력은 URL 에만 있지 않습니다. HTTP 헤더도 서버가 읽는 입력입니다.
랩의 `/debug` 는 헤더로 게이트되어 있습니다.

```bash
curl -s -o /dev/null -w 'X-Debug 없음: %{http_code}\n' http://127.0.0.1:8080/debug
curl -s -o /dev/null -w 'X-Debug: 1   : %{http_code}\n' -H 'X-Debug: 1' http://127.0.0.1:8080/debug
curl -s -H 'X-Debug: 1' http://127.0.0.1:8080/debug
```

```text
X-Debug 없음: 404
X-Debug: 1   : 200
routes=12 delay=0.25
```

경로를 정확히 맞혀도(`/debug`) 헤더가 없으면 **404로 존재 자체가 숨습니다.**
`X-Debug: 1` 을 실어야 200이 열립니다. 경로 퍼징만 하는 퍼저는 이 엔드포인트를
영원히 못 봅니다 — 경로는 맞았는데 헤더 축을 안 건드렸으니까요.

실무에서 헤더는 입력공간의 큰 축입니다. `X-Forwarded-For`(접근 제어 우회),
`Host`(가상호스트 라우팅), `User-Agent`(분기 로직), `Authorization`,
커스텀 `X-` 헤더. 이 모두가 퍼징 대상입니다.

## 5. 축 넷: 메서드

같은 경로라도 HTTP 메서드가 다르면 다른 동작입니다.

```bash
curl -s -o /dev/null -w 'GET  /login -> %{http_code}\n' http://127.0.0.1:8080/login
curl -s -o /dev/null -w 'POST /login -> %{http_code}\n' -d '' http://127.0.0.1:8080/login
```

```text
GET  /login -> 200    ← 폼을 보여준다
POST /login -> 401    ← 자격증명을 검사한다
```

`GET /login` 은 폼을 반환하고, `POST /login` 은 인증을 처리합니다.
경로는 하나인데 메서드에 따라 완전히 다른 코드 경로입니다.
`PUT`, `DELETE`, `PATCH`, `OPTIONS` 도 마찬가지 — 개발자가 깜빡하고
막지 않은 메서드가 우회로가 되는 일이 흔합니다.

## 6. 입력공간이라는 곱집합

정리하면 웹의 입력공간은 여러 축의 **곱**입니다.

```
입력 = 경로 × 파라미터(이름·값) × 헤더 × 메서드 × 본문 × 상태(세션)
```

각 축이 곱으로 붙기 때문에 전체 공간은 천문학적입니다. `/search` 하나만 해도
`q` 값이 무한하고, 거기에 헤더 조합, 메서드, 세션 상태가 곱해집니다.
**이 공간을 다 볼 수는 없다** — 그래서 퍼징이 필요합니다(Part 0 의 정의).

그리고 퍼징을 잘한다는 건, 이 축들 중 **어느 축을 이번에 퍼징할지**를
의식적으로 고른다는 뜻입니다. 축을 헷갈리면 헛발질합니다.

| 축 | 퍼징하는 장 |
|----|-------------|
| 경로 | 5·6장 |
| 파라미터 값 | 6장 (`/search?q=`) |
| 헤더 | 이 장에서 맛봄, 실무의 큰 축 |
| 메서드 | 이 장에서 맛봄 |
| 상태(세션) | 7장 |

## 정리

- 웹 입력공간은 경로 하나가 아니라 **경로 × 파라미터 × 헤더 × 메서드 × 상태**의 곱이다.
- 크롤은 링크된 표면만 본다. 퍼징은 잊힌 표면을 본다 — 이 랩에서 3배 차이.
- 경로를 정확히 맞혀도 헤더·메서드 축이 안 맞으면 표면이 숨는다(`/debug`).
- 퍼징을 잘한다는 건 **이번에 어느 축을 던질지 의식하는 것**이다.

다음 장(5장)은 이 지도의 첫 축 — 경로 — 를 실제로 퍼징합니다.
워드리스트가 어떻게 생성기가 되는지, 그리고 왜 워드리스트에 없는 건
영원히 못 찾는지를 봅니다.

```bash
docker compose down    # 실습 종료
```
