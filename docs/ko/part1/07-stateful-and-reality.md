# 7. 인증 상태 퍼징과 현실 — 레이트리밋·범위·윤리

**Part 1 · web2 감사**

5·6장의 퍼징에는 조용한 가정이 하나 있었습니다. **모든 요청이 동등하다.**
쿠키도 세션도 없이, 매 요청이 독립적으로 서버에 닿았습니다.

실제 애플리케이션의 흥미로운 표면은 대부분 로그인 뒤에 있습니다.
그리고 로그인 뒤의 퍼징은 두 가지 새 제약을 만납니다.
**상태**(요청이 이전 요청에 의존한다)와 **현실**(서버가 당신을 막는다).
이 장은 Part 1 을 그 두 벽에서 닫습니다.

## 이 장에서 답할 질문

- 인증이 필요한 표면을 어떻게 퍼징하는가 — 그리고 안 하면 무엇을 놓치는가
- `401` 은 왜 그 자체로 신호인가
- 레이트리밋은 방어자만이 아니라 퍼저의 결과도 어떻게 망치는가
- 실무에서 퍼징을 돌리기 전 계약서에 무엇이 있어야 하는가

## 5요소 위치

이 장이 다루는 요소: **생성 + 피드백**

| 요소 | 이 장에서의 형태 |
|------|------------------|
| 생성 | 5·6장과 동일 (워드리스트) |
| 변이 | 없음 |
| 오라클 | `401`·`429` 를 신호로 읽는다 (6장 오라클의 연장) |
| 피드백 | **인증 상태를 요청에 실어 나른다 — 세션이 곧 상태다** |
| 커버리지 | 없음 |

## 준비

```bash
cd labs/web2
docker compose up --build -d
curl -s http://127.0.0.1:8080/    # 200 이면 준비 완료
```

!!! danger "실습 범위"
    대상은 본인의 `127.0.0.1:8080` 컨테이너뿐입니다.
    이 장은 특히 **범위**를 다룹니다 — 남의 시스템에 이 실습을 그대로 옮기면
    범죄가 되는 이유를 곧 설명합니다. [범위와 안전](../scope-and-safety.md).

## 1. 401이라는 벽

인증 뒤의 API 엔드포인트를 찾는다고 합시다. 쿠키 없이 그냥 퍼징합니다.

```bash
printf 'notes\nprofile\nsettings\nadmin\nbilling\n' > ep.txt
ffuf -w ep.txt:FUZZ -u "http://127.0.0.1:8080/api/FUZZ" -mc all -t 5
```

```text
notes      [Status: 401, Size: 28, Words: 1, Lines: 2]
billing    [Status: 404, Size: 23, Words: 3, Lines: 2]
admin      [Status: 404, Size: 23, Words: 3, Lines: 2]
settings   [Status: 404, Size: 23, Words: 3, Lines: 2]
profile    [Status: 404, Size: 23, Words: 3, Lines: 2]
```

`/api/notes` 만 **401**, 나머지는 404입니다. 여기서 오라클을 한 단계 정교하게
읽어야 합니다. 401은 "없음"이 아닙니다. **"존재하지만 인증이 필요하다"**입니다.
404와 401의 차이가 곧 존재 여부의 누설입니다 — 6장의 403과 같은 원리입니다.

즉 인증 없이 퍼징해도 **엔드포인트의 존재는 열거됩니다.** 하지만 그 안이
무엇을 하는지, 어떤 파라미터를 받는지, 어떤 버그가 있는지는 401 벽 너머라
전혀 못 봅니다. 인증 뒤 표면을 퍼징하려면 상태를 들고 들어가야 합니다.

## 2. 상태를 획득한다: 로그인

세션 쿠키를 얻습니다. `curl -c` 로 쿠키를 파일(jar)에 저장합니다.

```bash
curl -s -i -c jar.txt \
     -d 'username=alice&password=wonderland' \
     http://127.0.0.1:8080/login | grep -iE 'HTTP/|location|set-cookie'
```

```text
HTTP/1.1 302 FOUND
Location: /account
Set-Cookie: session=sess-alice-860596105; HttpOnly; Path=/; SameSite=Lax
```

`jar.txt` 에 세션 쿠키가 담겼습니다. 이제 이 쿠키를 매 요청에 실으면
퍼저가 "로그인한 alice" 로서 서버에 닿습니다. 이게 **피드백**입니다 —
한 요청(로그인)의 결과가 이후 모든 요청의 상태를 바꿉니다.

## 3. 상태를 들고 재퍼징

같은 엔드포인트 퍼징을, 이번엔 쿠키를 실어서.

```bash
TOK=$(grep session jar.txt | awk '{print $NF}')
ffuf -w ep.txt:FUZZ -u "http://127.0.0.1:8080/api/FUZZ" \
     -H "Cookie: session=$TOK" -mc all -t 5
```

```text
notes      [Status: 200, Size: 48, Words: 3, Lines: 2]   ← 401 이 200 으로 열렸다
settings   [Status: 404, ...]
billing    [Status: 404, ...]
```

`/api/notes` 가 **401 → 200** 으로 바뀌었습니다. 인증 전후를 나란히 보면:

```bash
curl -s -o /dev/null -w 'no-cookie:   %{http_code}\n' http://127.0.0.1:8080/api/notes
curl -s -o /dev/null -w 'with-cookie: %{http_code}\n' -b jar.txt http://127.0.0.1:8080/api/notes
curl -s -b jar.txt http://127.0.0.1:8080/api/notes
```

```text
no-cookie:   401
with-cookie: 200
{"owner":"alice","notes":["todo: rotate keys"]}
```

여기서 이 장의 핵심 교훈이 나옵니다.

> 쿠키 없이 돌린 퍼징 결과 전체는, 인증 뒤 표면에 관한 한 무효다.

감사에서 "다 돌렸는데 별거 없더라"의 상당수가 이겁니다. 인증 상태를
안 들고 들어가서 401 벽만 두들기다 끝난 겁니다. 로그인 뒤 표면은
**같은 워드리스트, 같은 오라클, 다른 상태**로 다시 돌려야 합니다.

!!! tip "세션이 만료되면"
    퍼징 도중 세션이 죽으면 그 시점 이후 결과가 전부 401로 오염됩니다.
    긴 퍼징에서는 중간중간 로그인 상태를 확인하거나(예: `/account` 가
    200인지), ffuf 의 재인증 스크립트를 붙입니다. **인증은 한 번 얻고
    끝이 아니라, 유지해야 하는 상태입니다.**

## 4. 현실이라는 벽: 레이트리밋

로그인은 상태의 벽이었습니다. 다음은 현실의 벽입니다.
서버는 초당 수백 요청을 반기지 않습니다. 랩의 레이트리밋을 조입니다 —
10초에 20요청, 초과 시 429.

```bash
RATE_LIMIT=20 RATE_WINDOW=10 docker compose up -d --force-recreate
```

무례하게, 스레드 20으로 퍼징합니다.

```bash
ffuf -w wordlists/teaching.txt:FUZZ -u "http://127.0.0.1:8080/FUZZ" \
     -mc all -t 20 -o r1.json -of json
jq -r '.results[].status' r1.json | sort -n | uniq -c
```

```text
   1 200
   1 403
  18 404
  41 429     ← 61건 중 41건이 레이트리밋에 막힘
```

재앙입니다. 처음 20요청만 통과하고 나머지 41건이 429로 튕겼습니다.
그 41건 안에 진짜 히트(`/.env.bak`, `/backup.zip` 은 이미 통과했지만
다른 실행 순서라면 얼마든 묻힐 수 있습니다)가 섞여 있었다면
**영영 못 봅니다.** 레이트리밋은 방어자를 위한 것이지만,
동시에 무례한 퍼저의 **결과 품질을 직접 망칩니다.**

그리고 서버는 어떻게 기다려야 하는지도 알려줍니다.

```bash
curl -s -i http://127.0.0.1:8080/ | grep -iE 'HTTP/|retry-after'
```

```text
HTTP/1.1 429 TOO MANY REQUESTS
Retry-After: 10
```

`Retry-After: 10` — "10초 뒤에 다시 와라". 이 헤더를 무시하고 계속 두들기면
그게 부하 공격입니다.

## 5. 예의가 곧 정확도다

처방은 간단합니다. **요청률을 서버가 감당할 수준으로 낮춘다.**
ffuf 의 `-rate` 는 초당 요청 수의 상한입니다. `-rate 1` 로 다시.

```bash
ffuf -w wordlists/teaching.txt:FUZZ -u "http://127.0.0.1:8080/FUZZ" \
     -mc all -rate 1 -o r2.json -of json
jq -r '.results[].status' r2.json | sort -n | uniq -c
```

```text
   5 200
   1 403
  55 404
```

**429가 하나도 없습니다.** 그리고 -t 20 실행에서 429에 묻혔던 히트들이
전부 돌아왔습니다 (200이 1개 → 5개). 느려진 대신 **완전**해졌습니다.

이게 이 장이 6장의 오라클 사다리에 얹는 마지막 교훈입니다.
좋은 오라클로 신호를 잘 읽어도, **요청률이 무례하면 신호 자체가
429에 파묻혀 도달하지 못합니다.** 예의는 매너의 문제가 아니라
탐색의 완전성 문제입니다.

## 6. 현실: 범위·권한·윤리

지금까지의 모든 실습은 본인이 띄운 컨테이너를 대상으로 했습니다.
이유를 이제 정면으로 말합니다.

**허가 없이 남의 시스템을 퍼징하는 것은 범죄입니다.**
퍼징은 그 성격상 대량의 비정상 요청을 보냅니다. 방금 봤듯이
레이트리밋을 넘기면 서버에 실제 부하를 만듭니다. 한국에서는
정보통신망법 위반, 경우에 따라 업무방해로 다뤄질 수 있습니다.
"취약점을 알려주려 했다"는 동기는 면책이 되지 않습니다.

그래서 실무 감사에서 퍼징을 돌리기 전, 계약서(또는 버그바운티 정책)에
다음이 명시되어 있어야 합니다.

| 항목 | 왜 |
|------|-----|
| 대상 호스트·도메인 목록 | 와일드카드 범위는 서드파티 자산을 삼킨다 |
| **제외 대상** | 결제·메일·SMS 등 부수효과가 외부로 나가는 경로 |
| 허용 시간대 | 퍼징은 부하를 만든다 — 피크 타임을 피한다 |
| **요청률 상한** | 상한 없는 퍼징은 사실상 부하 테스트다 (방금 봤다) |
| 긴급 연락 체계 | 장애를 냈을 때 즉시 멈추고 알릴 상대 |

특히 **부수효과 있는 엔드포인트**는 격리 환경이 아닌 한 대상에서 뺍니다.
퍼징은 어떤 입력이 들어갈지 모른다는 전제 위에서 돕니다. 계정 삭제,
결제, 메일 발송 경로에 무작위 입력을 던지면 실제로 계정이 지워지고
메일이 나갑니다.

!!! warning "버그바운티도 무제한이 아니다"
    공개 버그바운티 프로그램에 참여할 때도, 그 프로그램이 자동화 스캐닝과
    퍼징을 **명시적으로 허용**하는지 먼저 확인하십시오. 다수가 금지하거나
    요청률을 제한합니다. 정책 위반은 포상은커녕 법적 문제를 부릅니다.

## Part 1 정리

web2 감사를 다섯 요소로 관통했습니다.

- **생성**(5장): 워드리스트가 곧 생성기. 없는 후보는 못 찾는다.
- **오라클**(6장): 코드 → 크기 → 시간의 사다리. 신호가 약할수록 잡음에 취약하다.
- **피드백**(7장): 인증 상태를 실어 나른다. 재귀·세션이 순수 생성을 루프로 바꾼다.
- **현실**(7장): 레이트리밋은 결과 품질을 망친다. 예의가 곧 완전성이다.
- **범위**(7장): 대상은 언제나 허가된, 격리된 시스템이다.

Part 2 에서 같은 다섯 요소가 API 로 넘어갑니다. 거기선 워드리스트 대신
**OpenAPI 스키마가 생성기**가 되고, 크기·시간 대신 **스키마 위반이
오라클**이 됩니다. 도구와 신호가 바뀔 뿐, 질문은 같습니다.

```bash
docker compose down    # 실습 종료
rm -f ep.txt jar.txt r1.json r2.json
```
