# 10. 상태저장 시퀀스 퍼징 — 호출 순서라는 입력

**Part 2 · API 감사**

지금까지 각 요청은 독립적이었습니다. 8·9장은 오퍼레이션 하나하나를
따로 두드렸습니다. 하지만 실제 API 의 흥미로운 버그는 **여러 요청 사이**에
있습니다. 등록하고 → 로그인하고 → 그 토큰으로 접근하는, 순서가 있는 흐름.

이 장의 통찰은 하나입니다. **호출 순서 자체가 입력공간의 한 축이다.**
7장에서 세션을 "상태"라 불렀듯이, 여기선 요청들의 나열이 상태를 만듭니다.

## 이 장에서 답할 질문

- 왜 오퍼레이션을 따로 퍼징하면 놓치는 버그가 있는가
- Schemathesis 는 요청들의 순서를 어떻게 알아내는가 (API 링크)
- 상태 시퀀스 퍼징은 5요소의 무엇에 해당하는가

## 5요소 위치

이 장이 다루는 요소: **생성 + 피드백**

| 요소 | 이 장에서의 형태 |
|------|------------------|
| 생성 | 스키마 기반 (8장) |
| 피드백 | **한 응답의 출력을 다음 요청의 입력으로 잇는다 — 이 장의 전부** |
| 오라클 | 9장 계약 검사 + 시퀀스 끝의 상태 |

## 준비

```bash
cd labs/api
docker compose up -d
curl -s http://127.0.0.1:5005/createdb
```

## 1. 독립 요청의 맹점

VAmPI 의 `/me` 는 "현재 로그인한 사용자 정보"를 돌려줍니다.
이걸 따로 퍼징하면 어떻게 될까요? 토큰이 없으니 401 만 나옵니다.
9장 끝에서 본 "인증 벽"입니다.

`/me` 를 의미 있게 시험하려면 **먼저** `/users/v1/register` 로 계정을 만들고,
**그 다음** `/users/v1/login` 으로 토큰을 얻고, **그 토큰을** `/me` 에
실어야 합니다. 세 요청이 순서대로, 앞의 출력이 뒤의 입력이 되어야 합니다.

```
register(user) → login(user) → token → me(token)
```

오퍼레이션을 따로 퍼징하면 이 흐름을 영영 못 만듭니다.
**순서가 곧 입력**인데, 순서를 안 만들었으니까요.

## 2. API 링크 — 순서를 선언하다

OpenAPI 는 이 연결을 **링크(links)**로 표현할 수 있습니다.
"이 응답의 이 필드를 저 요청의 저 파라미터로 쓴다"는 선언입니다.
스키마에 링크가 명시돼 있으면 Schemathesis 가 그대로 따르고,
없어도 필드 이름의 유사성으로 **추론**합니다.

상태저장 페이즈만 돌려봅니다.

```bash
.venv/bin/schemathesis run http://127.0.0.1:5005/openapi.json \
  --url http://127.0.0.1:5005 --phases stateful --max-examples 30
```

```text
❌  Stateful (in 2.37s)
    Scenarios:    86
    API Links:    2 covered / 22 selected / 22 total (22 inferred)
    ✅ 80 passed  ❌ 6 failed
```

읽는 법:

- **22 inferred** — Schemathesis 가 오퍼레이션 사이의 연결 22개를 추론했습니다.
  예: register 의 출력 username → login 의 입력, login 의 출력 token → 인증 헤더.
- **86 scenarios** — 그 링크들을 엮어 86가지 호출 시퀀스를 만들어 실행했습니다.
- **6 failed** — 그중 6개 시퀀스가 계약을 어겼습니다.

**86개의 시퀀스를 사람이 안 짰습니다.** 스키마의 구조에서 순서가
자동으로 생성됐습니다. 이게 상태 시퀀스 퍼징의 생성기입니다.

## 3. 이것이 피드백인 이유

2장에서 피드백을 "한 실행의 결과로 다음 입력을 바꾸는 것"이라 정의했습니다.
커버리지 퍼저는 새 코드를 연 입력을 코퍼스에 보존해 되먹였습니다.

상태 시퀀스는 다른 종류의 되먹임입니다. **한 요청의 응답(토큰, 생성된 ID)이
다음 요청의 입력이 됩니다.** login 의 출력 토큰이 없으면 me 요청을 만들
수 없습니다 — 앞 결과가 뒤 입력을 결정합니다. 이 데이터 의존이 곧 피드백이고,
독립 퍼징이 못 가는 깊이로 데려갑니다.

| 피드백의 종류 | 무엇이 되먹여지나 | 어디서 |
|---------------|------------------|--------|
| 커버리지 | 새 경로를 연 입력 → 코퍼스 | 2장, Part 3 |
| 재귀·세션 | 발견·인증 상태 | 5·7장 |
| 데이터 의존 | 응답 값 → 다음 요청 | **이 장** |

## 4. 순서가 열어주는 표면

시퀀스를 만들 수 있게 되자 인증 벽 너머가 열립니다.
register → login 으로 유효한 토큰을 손에 넣었으니, 이제 그 토큰으로
인증이 필요한 오퍼레이션들(`/me`, `/users/v1/{username}/password` 등)을
**진짜로** 시험할 수 있습니다.

그리고 바로 여기서 VAmPI 의 핵심 취약점이 드러납니다. 유효한 토큰을 든
사용자가, **자기 것이 아닌** 자원에 접근할 수 있는가? 이게 BOLA 이고,
계약(스키마)만으로는 안 잡히는 인가 버그입니다. 다음 장(11장)의 주제입니다.

!!! tip "상태 시퀀스의 한계"
    Schemathesis 의 링크 추론은 필드 이름에 의존합니다. 이름이 안 맞으면
    (`user_id` vs `id`) 링크를 못 잇습니다. 복잡한 워크플로우는 스키마에
    링크를 명시하거나, 시나리오를 직접 코드로 씁니다. 자동 추론은 출발점이지
    종착점이 아닙니다.

## 정리

- 호출 순서 자체가 입력공간의 한 축이다. 독립 퍼징은 이 축을 안 건드린다.
- OpenAPI 링크(명시 또는 추론)가 순서의 생성기다 — 22개 링크에서 86개 시퀀스.
- 한 응답이 다음 요청의 입력이 되는 데이터 의존이 곧 피드백이다.
- 시퀀스로 유효 토큰을 얻으면 인증 벽 너머 — 인가 버그(BOLA)로 간다.
