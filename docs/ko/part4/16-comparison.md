# 16. 세 도메인 5요소 비교

**Part 4 · 회고**

15개 장을 지나왔습니다. 장난감 퍼저부터 스마트컨트랙트 불변식까지,
도구는 `ffuf`·`Schemathesis`·`forge` 로 완전히 달랐습니다. 이 마지막 장은
한 걸음 물러서서, **그 모든 게 하나의 뼈대였음**을 확인합니다.

1장의 정의를 다시 봅니다.

> 퍼징이란, 너무 커서 다 볼 수 없는 입력공간을, 유한한 시간 안에,
> 버그가 있을 법한 쪽으로 편향되게 탐색하는 일이다.

web2·API·web3 는 이 정의의 세 가지 구현이었습니다. 이제 5요소별로
나란히 놓습니다.

## 5요소 종합 비교

### 생성 — 입력을 어디서 가져오나

| 도메인 | 생성기 | 입력 단위 |
|--------|--------|-----------|
| web2 (5장) | 워드리스트 | 경로·파라미터 문자열 |
| API (8장) | OpenAPI 스키마 | 구조화된 요청 (경로+메서드+본문) |
| web3 (13·14장) | 함수 시그니처 + 핸들러 | 함수 호출 (선택자+인자+순서) |

생성기의 원천이 "사람이 모은 단어" → "기계가 읽는 스키마" → "코드의
타입 자체"로 옮겨갑니다. 뒤로 갈수록 생성이 자동화되지만, 대신
**무엇을 유효한 입력으로 볼지**(스키마, 핸들러)를 정의하는 부담이 커집니다.

### 오라클 — 무엇을 버그라 부르나

| 도메인 | 주 오라클 | 종류 (3장 분류) |
|--------|-----------|------------------|
| web2 (6장) | 응답 코드·크기·시간 차분 | 차분 + 타임아웃 |
| API (9·11장) | 스키마 계약, 5xx, 인가 불변식 | 크래시 + 형태 + 불변식 |
| web3 (15장) | 회계 불변식 | 불변식 |

이게 이 교재의 가장 중요한 관통선입니다. **도메인이 깊어질수록 오라클이
"관찰된 신호"에서 "선언된 불변식"으로 이동합니다.** web2 는 우리가 바깥에서
크기 차분을 관찰해 오라클을 만들었습니다. web3 는 감사자가 "항상 참이어야
할 등식"을 선언해야 했습니다.

그리고 세 도메인 공통의 교훈: **가장 가치 있는 버그는 자동 오라클이
못 잡고, 사람이 불변식을 써야 하는 곳에 있습니다.** web2 의 사용자 열거,
API 의 BOLA, web3 의 self-transfer 인플레 — 셋 다 "형태는 정상인데
의미가 틀린" 버그였고, 도구가 아니라 사람의 통찰이 잡았습니다.

### 피드백 — 결과로 다음을 바꾸나

| 도메인 | 피드백 형태 | 되먹여지는 것 |
|--------|-------------|----------------|
| 기초 (2장) | 커버리지 가이드 | 새 코드 경로를 연 입력 → 코퍼스 |
| web2 (5·7장) | 재귀·세션 | 발견된 디렉토리, 인증 상태 |
| API (10장) | 데이터 의존 | 응답 값(토큰·ID) → 다음 요청 |
| web3 (14장) | 상태 누적 | 트랜잭션이 남긴 온체인 상태 |

피드백의 유무가 얼마나 결정적인지는 2장에서 봤습니다 — 같은 버그를
커버리지는 수천 회에, blind 는 300만 회에도 못 찾았습니다. 피드백의
구체적 형태는 도메인마다 다르지만, 본질은 하나입니다.
**단발 입력이 아니라 시퀀스를 탐색한다.**

### 커버리지 — 얼마나 봤는지 아나

| 도메인 | 커버리지 척도 |
|--------|---------------|
| 기초 (2장) | 밟은 코드 줄 (`sys.settrace`) |
| web2 | 대체로 없음 (블랙박스) |
| API | 오퍼레이션·상태코드 커버리지 |
| web3 (14장) | 실행된 함수·분기, 핸들러 호출 분포 |

web2 블랙박스 퍼징은 커버리지가 거의 없었습니다. 그래서 오라클과
워드리스트 품질에 전적으로 의존했습니다. web3 invariant 퍼징은 다시
커버리지로 돌아왔습니다 — 어느 함수가 얼마나 호출됐는지(14장의 revert
분포)가 곧 탐색 품질의 척도였습니다.

## 하나의 격자로 보기

전체를 한 장으로 압축하면:

| 요소 | web2 | API | web3 |
|------|------|-----|------|
| **생성** | 워드리스트 | OpenAPI 스키마 | 함수+핸들러 |
| **변이** | (거의 없음) | 스키마 경계값 | 인자 bound |
| **오라클** | 코드·크기·시간 차분 | 스키마 계약·BOLA | 회계 불변식 |
| **피드백** | 재귀·세션 | 데이터 의존 시퀀스 | 상태 누적 |
| **커버리지** | 없음 | 오퍼레이션 | 함수·분기 |

세로줄(도메인)은 완전히 다른 도구·어휘·공동체입니다. 가로줄(요소)은
그 전부를 관통합니다. **하나를 배우면 나머지가 빠른 이유가 이 격자입니다.**

## 무엇을 가져갈 것인가

이 교재를 덮으며 남길 것 셋.

**1. 도구는 요소의 구현일 뿐이다.** `ffuf` 가 `httpx` 로 바뀌고,
Schemathesis 가 다른 도구로 바뀌고, Foundry 가 업데이트돼도, 다섯 요소는
그대로입니다. 새 도구를 만나면 물어보십시오 — "이건 어느 요소를 어떻게
구현했나?" 그러면 문서 없이도 감이 옵니다.

**2. 오라클이 승부처다.** 생성기는 대충 만들어도 언젠가 정답을 던집니다.
오라클이 약하면 그 정답을 그냥 흘려보냅니다. "퍼징 돌렸는데 안 나왔다"의
절반은 오라클 문제입니다. 크래시만 보고 있지 않은지, 불변식을 겨냥했는지
항상 되물으십시오.

**3. 범위와 권한을 먼저.** 모든 랩은 로컬 타겟이었습니다. 실무에서 이
기술은 강력한 만큼 위험합니다 — 허가 없는 퍼징은 범죄입니다. 계약된 범위,
요청률 상한, 부수효과 제외를 먼저 확인하는 습관이 기술보다 앞섭니다
(7장·[범위와 안전](../scope-and-safety.md)).

## 다음으로

이 교재는 각 도메인의 입문에서 멈췄습니다. 더 깊이 가려면:

- **커버리지 가이드 퍼징 정통**: AFL++, libFuzzer — 2장의 원리를 C/C++/Rust 로
- **web2 심화**: 인증·비즈니스 로직 퍼징, GraphQL·gRPC
- **API 심화**: 상태 머신 모델링, 계약 위반의 자동 분류
- **web3 실전**: [damn-vulnerable-defi](https://www.damnvulnerabledefi.xyz/),
  Echidna·Medusa, 실제 감사 리포트 읽기

어디로 가든, 다섯 요소의 격자를 들고 가십시오. 그게 이 교재가 남기려는
전부입니다.
